# 突发流量压测

数字来自 `docs/bench-results/realistic/` 里的 k6 summary、按秒 CSV 和对账 JSON。QPS 和延迟保留两位小数，笔数用整数。`http_req_duration` 的单位是毫秒，`med` 是 P50。

goodput 只算新预扣：HTTP 200 且响应里 `replay=false`（k6 计数器 `grab_success`）。回放、已拥有、售罄、429、失败分开报，不进 goodput。

入口拒绝率 = (`grab_limited` + `grab_failed`) / 请求数。`grab_failed` 是 429 和 409 以外的失败，包括 404 和 5xx。

## 流量形状

`scripts/k6/realistic.js`，`ramping-arrival-rate`：2 秒拉到 2000 次/秒，保持 3 秒，2 秒降到 300 次/秒，再保持 8 秒。8 张券，普通用户按 Zipf（s=1.1）选券，下标 0 最热。请求构成是代码里的概率：60% 新用户、20% 机器人（32 个账号死磕最热券，每次换幂等键）、10% 同一幂等键重试、10% 同一人换新幂等键。

修复后那一轮（`fixed.json`）实际抽到的比例：新用户 7647（60.0%），机器人 2521（19.8%），回放 1327（10.4%），换键再点 1254（9.8%）。`dropped_iterations` 没有出现，到达率被 k6 排进去了。

修复后容量轮按秒的到达（`fixed-per-second.csv`）开头是 44、786、1731、2000、1884、2088，然后落到 300 左右。峰值那一秒是 2088 次请求。

`COMBINED_HOTPATH=0`，`GLOBAL_RPS=0`，用户限流 30 次/10 秒。两台 API 的雪花 worker 分别是 1 和 2。库存都是 8 个桶、`sharded`，容量轮每张 80000，避免售罄把 goodput 截断。

## 优化前后

优化是多实例下的券模板缓存。本地布隆过滤器说「没有」就直接 404 时，创建券的那台 API 认识这张券，另一台不认识。nginx 轮询把大约一半请求打成 404。修复后，本地未命中会读 Redis 里的券模板，Redis 没有才 404，随机 id 仍然不查 MySQL。两轮都是 `COMBINED_HOTPATH=0`，同一脚本、同一机器、同一 cgroup。

修之后 8 张券的已落库订单（热到冷）：3184、1339、947、644、571、409、362、303，合计 7759，和新预扣笔数相同。最热是最冷的 3184/303 = 10.5 倍。机器人固定打最热的那张，所以比纯 Zipf 更尖。

api1 顶在自己的 0.35 CPU 上，api2 几乎空闲。延迟已经降到毫秒内时，并发连接很少，nginx 的 keepalive 把上游连接留在了先连上的那台。第二台 API 没有接住峰值。Redis 离 1 个核还远；同一次采样里 `instantaneous_ops_per_sec` 是 25097（`fixed-redis-info.txt`，只是那一瞬间）。MySQL 到了 63.5%，那是消费者在写订单，抢券请求本身不等这条路径。

所以这轮的瓶颈是「流量粘在一台已经被 cgroup 卡住的 API 上」，不是 Redis 单线程，也不是分桶。

## 上游连接改均衡之后

## 过期订单取消

以前每秒只领 `expire_at` 最老的 100 张。`2026-09-28T08:21:35Z` 时过期未取消是 514657 张，新超时的单排在这批后面。

现在 4 个协程一直扫。偶数协程只领「`expire_at` 落在现在往前 3 秒」的单，奇数协程用 `idx_status_expire` 从最老的开始清积压。领取是 `SELECT ... ORDER BY expire_at LIMIT 200 FOR UPDATE SKIP LOCKED`，在同一个事务里改成 `CANCELLED`，提交后再跑还库存 Lua。

第一张证明券是 144，库存 20，支付超时 2 秒。开测时过期未取消是 889787 张。订单 `362878847907012608`：`updated_at - expire_at` = 0.066 秒，观察到 Redis 8 个桶加回 20 并且用户集合为空，是过期后 0.085 秒。对账 `consistent=true`、`oversell=0`，`DBCancelled=1`，`UnreturnedCancels=0`，Redis 剩余 20。

第二张是券 145，当时过期未取消还有 864387 张。`updated_at - expire_at` = 0.269 秒，库存加回去是过期后 0.289 秒。对账同样 `oversell=0`、Redis 剩余 20、取消 1 张、未还库存 0。

清积压的速度用 MySQL 自己的时间戳量了一次：`08:34:30.587` 还有 750187 张，`08:34:50.576` 还有 738187 张。19.989 秒里少了 12000 张，合每秒 600.33 张。按这个速度，75 万张旧单还要大约 750187/600.33 = 1249.6 秒才会排空。刚到期的单不排在这后面，上面两张的 0.066 秒和 0.269 秒就是在积压还在的时候量的。

## 故障

都在修复之后、`COMBINED_HOTPATH=0` 上做。

### 杀掉 api2

`fixed-chaos-api-events.log`：08:15:16Z `docker kill`，08:15:21Z `docker start`，同一秒 healthz 成功。客户端 `grab_failed=0`，checks 12748 通过、0 失败。全程 P99 20.74 ms，goodput 514.20/秒。到达率从 2001 掉到 300 的形状和没有杀进程的那一轮一致，是脚本里的回落，不是实例被杀之后的故障。8 张券对账 `oversell=0`。

实例缺席了大约 5 秒。这段时间 nginx 把请求交给还活着的 api1，客户端没有 5xx。进程拉起后，健康检查在启动的那一秒就过了。

### 重启 Redis

08:15:32Z `docker compose restart redis`，08:15:48Z `PING` 成功，间隔 16 秒。k6 在 08:15:34Z 到 08:15:41Z 这 8 个秒里 `grab_failed` 分别是 38、38、311、383、451、650、276、178，合计 2325。checks 失败 2241（5xx 比例 2241/11795 = 19.00%）。`dropped_iterations` 954。全部请求 P99 5000.09 ms、最大 5001.13 ms（客户端超时 5 秒）。期间成功的请求 P99 是 17.74 ms。

k6 在 Redis 恢复之前就结束了，所以恢复之后的延迟不在这份 summary 里。随后 8 张券对账全部 `consistent=true`、`oversell=0`。

### 中途停消费者

最热券 111，库存 200000。08:15:53Z 停消费者。

| | 刚停下 `fixed-chaos-consumer-mid.json` | k6 结束仍停着 `...-held.json` | 拉起之后 `...-final.json` |
|---|---:|---:|---:|
| 时刻 | 08:15:55Z | 08:16:04Z | 08:16:13Z 账平 |
| DB 有效订单 | 1910 | 1910 | 3089 |
| Redis 用户 | 2523 | 3089 | 3089 |
| Redis 剩余 | 197477 | 196911 | 196911 |
| oversell | 0 | 0 | 0 |
| consistent | false | false | true |

停着的时候 DB 钉在 1910。结束时用户集合减已落库 = 3089 − 1910 = 1179，总库存减（Redis 剩余 + 已落库）= 200000 − (196911 + 1910) = 1179。两边相等，`oversell=0`。08:16:04Z 拉起消费者，08:16:13Z 对账退出码 0，大约 9 秒。196911 + 3089 = 200000，lag 0。其余 7 张券随后也是 `consistent=true`、`oversell=0`。

这轮 k6 本身没有 5xx（`grab_failed=0`），goodput 507.11/秒，P99 26.31 ms。停消费者不影响抢券接口，只让落库落后。

## 这组实验没有覆盖的

Redis 仍然是一个实例。`kill -9` 之后没有再开一轮 k6 去量恢复后的 P99，只做了对账。AOF `everysec` 理论上会丢最后一秒，这一轮被杀掉期间新建的 8 张券对账是平的，没有换一套数据把丢秒重现出来。

取消速度是在 0.50 CPU 的消费者和 0.70 CPU 的 MySQL 上量的。每秒大约 600 张旧单，积压本身没有在这轮压测结束前排空。
